# DX12-1 — DX12 black terrain, FSR 4 fallback, upscaler transition log

## Problem

1. **DX12 terrain rendered black or white** with popping buildings (owner report, Nogova editor).
   The terrain's ground-texture array sits first in its bind group. wgpu-hal's DX12 backend
   copies only the descriptors it is given for a partially bound array, but lays out the
   bindings after it using the array's full declared size (4096). The index map, detail and
   jitter bindings therefore read as empty. One render phase cost about 14 ms on DX12 as a
   side effect.
2. **FSR 4 chosen on Vulkan fell to bilinear**, not FSR 3.1 or FSR 1. `GraphicsApply.cpp`
   turned off `fsrOn` and `fsr31On` for `dlssMode 3`, so once FSR 4 reported "needs DX12" the
   chain had nothing left but the bilinear pass. Nothing in the log said which backend ran.
3. The log line "DLSS status: inactive … FSR 1 is the upscaler" was hard-coded for non-DLSS
   builds, so it named a backend that was not necessarily running.

## Approach

- `terrain/mod.rs` (`Terrain::new`): on DX12 the ground array is padded to its full declared
  size. The `partially_bound` flag is cleared when the active backend is DX12. Vulkan is
  unchanged.
- `GraphicsApply.cpp`: `dlssMode 3` (FSR 4) also enables FSR 1 and FSR 3.1 as fallbacks,
  the same way mode 4 already keeps FSR 1. The chain order (DLSS > FSR 4 > FSR 3.1 > Native
  TAA > FSR 1 > Bilinear) then picks the next available backend off DX12.
- `lib.rs`: logs `upscaler: active is now <name>` on each change of the backend that ran.
  Tracked separately from the per-frame readout (`last_upscaler` is reset to native every
  frame), so the line is logged once per transition, not once per frame.
- `dlss_status.rs`: the non-DLSS reason no longer names a fallback.
- `fsr4.rs`: `describe()` gives the texture format, size, sample count and usage in the
  "not a DX12 resource" messages. Used to diagnose device loss, which looked like a texture bug.
- `scripts/Shot-Mission.ps1` (new): runs a dev mission through `--harness`/`--test-mission`
  on Vulkan or DX12, takes screenshots and keeps the engine log, so checks need no desktop.
- `docs/KNOWN_ISSUES.md`: the two fixed entries.

## Evidence

- jeep-ride on DX12 vs Vulkan: sand terrain (201,179,149) vs (212,191,160); screenshots match.
  foliage-rays and tw-showcase match on both backends. No device loss or validation errors.
- `Shot-Mission.ps1` upscaler check, build 104, jeep-ride:
  - Vulkan: `upscaler: active is now FSR 3.1` (previously bilinear with the saved FSR 4 mode).
    Screenshot renders correctly.
  - DX12: `upscaler: active is now FSR 4` (FSR 4.1.1 context 858x482 → 1280x720).
- `cargo test -p wgpu_renderer --lib -- --test-threads=1`: 719 passed, 4 failed, 5 ignored.
  The 4 failures predate this ticket: `exported_abi_version_matches_the_public_contract`,
  `every_world_geometry_family_takes_the_same_aerial_perspective`, and two GI probe tests
  (16 sampled-texture limit on the test device).
- Parallel `cargo test` once hit `STATUS_ACCESS_VIOLATION` (exit 0xc0000005) during GPU tests.
  Not reproduced single-threaded. Flagged, not fixed here.
- `dlss_status` tests: 14/14 pass.

## Risks

- The terrain padding depends on wgpu-hal's partially bound array behaviour. Re-check it on
  any wgpu upgrade, and remove the workaround if the bug is fixed upstream.
- FSR 4 mode on Vulkan now runs FSR 3.1 rather than bilinear. That is a visible change for
  anyone who saved mode 3 on Vulkan.
